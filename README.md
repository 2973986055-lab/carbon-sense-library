三策略主面板比较同一日需求下的用电、室温和到场表现。供冷不足、人数与全关矛盾、零人数代理、温度变化归因和关灯照度约束仍
在相关操作旁提示。旧版预设算例集中到折叠区域，不用于新版成果展示。

`data/dashboard-layout.css`负责本轮版面，`data/dashboard-layout.js`负责展开锚点
对应资料；原计算及数据继续使用现有模块，没有更换技术栈。布局仅本地更新，未发布。

## 连续温度与三策略情景初版（2026-10-12，原全开照明对照）

用户确认使用时段室温目标23—24℃，允许预测到场前提前开启空调。提前时长尚无
具体现场上限，本版比较0、15、30分钟的假设，默认30分钟不代表已核实的设备运行规则。

`data/control-scenario-model.js`实现单区有效热容的连续温度平衡，采用常输入时段的
解析指数解；不是完整EnergyPlus模拟或已校准建筑数字孪生。初始室温28℃、热容倍数10
是可编辑假设，另比较初值24/26/28℃与倍数5/10/20的9组情景。方法参考EnergyPlus
区域热平衡与有效热容文档，数值不是从本房间实测反演。玻璃、换气、SHR、COP/部分负荷
性能及未核实的建筑边界仍沿用明确假设，9组分析不覆盖全部不确定性。

三种模式面对相同的训练期登记时长校准人数代理、历史天气和初始室温，并采用同一全开照明规则：
日常基准从首次情景有人开始日间保持启用，21:00以后首次当前代理人数为零时关闭；
21:00是情景边界，非学校关机时间。实时模式响应当前情景占用；预测模式沿用实时规则，
在当前空置且冻结30分钟趋势预测有需求时，按所选提前时长允许供冷。控制不读取未来
实际需求或天气。控制器假定知道当前情景人数及模型室温，未接入现场感知，不向设备发指令。
6/24—28的场景含当日拟合信息，界面标记训练期回放，仅作演示；6/29以后为训练期外
情景。后者也不构成实测控制验证，不能将室温合格率解释为已验证的传感器达标率。

默认三种温控目标均24℃；日常设定23—24℃可编辑，改变时需区分设定温度差的贡献。
供冷采用相同理想调节及原通用部分负荷功率换算，不模拟压缩机保护、风机待机或实测
性能曲线。1分钟是数值步长，输入每半小时保持；22:00需求延续到22:30也是保持假设。
一天内室温连续，各天初值独立，不能把各日当作已经校准的连续一周仿真。

温度合格率按代理有人时段的数值步长末室温统计，不是实际监测或综合舒适度。结果允许
零节电或负节电；若白天没有代理空置且目标相同，日常与实时可能相同。提前供冷可以改善
到场室温并增加用电，界面直接显示取舍。主面板保留三模式，原独立0.5小时模型作为试算
与依据保留，不能混用其湿度输出作为连续动态测量。旧9.34%不作为本模型成果。

动态测试：`node tests/control-scenario.test.cjs`，验证热平衡解析解、同需求与同照明、
0分钟前置与实时等价、未来数据隔离、容量不足、低温不能虚构供热、空置规则及7日计算。

## 本地运行

这是无构建步骤的静态网站，直接打开 `index.html` 即可，也可以使用任意静态文件服务器。

规则回归测试：`node tests/interactive-model.test.cjs`，覆盖人数0—314、温度22—34℃、
高温约束、空置、满座、手动覆盖、可变时长、精确输入修正和报告参考数据不被修改。
迁移预测测试：`node tests/reservation-model.test.cjs`，覆盖时刻、容量限制、异常输入、
拟合与预测公式、时间留出边界和全馆评估口径。

默认同条件零节电、负节电、容量不足、空置与16组合敏感性。数字和显示精度不代表实测精度。
运行基准测试：`node tests/operating-baseline.test.cjs`，覆盖预约零值不自动停机、
显式全关、独立照明、23—24℃对照、配对敏感性及设备来源一致性。
