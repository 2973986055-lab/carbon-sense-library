# 六组四区照明—空调联算复现

在仓库根目录运行（已用 Node.js 24.18.0 逐字验收；脚本只使用内置模块，不安装依赖）。不同 JavaScript 引擎或版本的浮点末位若有差异，哈希校验会提示而不会默默放行：

```sh
node scripts/reproduce-joint-evidence.cjs
```

脚本读取仓库内的预约代理、ERA5历史天气、设备与四区模型代码，对 2026-06-29、2026-06-30 分别在 300、1000、5000 W/K 混合假设下重跑日常基准、实时感知、预测协同三策略。每组产生 192 个5分钟回放点。脚本是**只读校验**：逐字比对本目录的六份冻结原始回放，并核对分项适配结果、`data/joint-evidence-data.js`、`data/joint-space-evidence-data.js`、`data/joint-forecast-action-data.js`及两个清单的 SHA-256；不修改网站数据。成功时输出 `"passed": true`，任何差异会报错退出。

每个回放点的`minute`和`time`是5分钟区间的**起点**，例如09:05表示09:05—09:10。人数与灯状态是该区间的情景输入，空调用电为区间累计值（网页功率为5分钟平均），四区`endingC`是区间结束时的模型室温。网页游标显示完整区间，避免把末温误写为起点的温度实测。

数据与代码边界：

- `data/reservation-profile.js` 与 `data/reservation-source.json` 是全馆半小时预约统计及一楼签到至签退总时长形成的代理资料，不含个人预约记录；签到时长**未扣暂离**，不是一楼逐时实际在座。
- `data/environment-dataset.js` 含合并的历史预约代理与附近 ERA5 网格再分析天气。天气来自 [Open-Meteo 历史天气接口](https://open-meteo.com/en/docs/historical-weather-api)，其数据来源与许可见文件内元数据；约25公里网格不能代表室内或校园实测。
- 四区人员位置、14组灯位、自然光与照度、300/1000/5000 W/K 混合系数、室温与空调运行响应均是未现场校准的模型假设。两台空调的名义耗电按额定输入与模型运行时长换算，没有历史电表、室内温度或桌面照度实测。
- 合并输入文件的设备元信息仍写“第二台同规格待核实”。[设备来源更正记录](equipment-provenance-correction.json)逐字标出旧字段、两份源文件哈希和用户于2026-10-11确认两台同规格的依据；复现脚本会核对它。第二台铭牌照片仍未取得，额定输入也不是运行功率实测。更正记录不改冻结输入或六组结果。
- 6月29—30日已被反复用于模型开发检查，不是未触碰的新验证集。原始回放 JSON 保留了模型内部合计字段用于能量守恒核对；**网站只分别展示照明和空调用电**，不能把内部合计或分项差值表述为合格、实测节电。
- 预测动作审计只把同一预测轨迹状态下，冻结人数预测与当前人数保持的候选空调指令直接比较；“选用预测分支”即使发生，也可能发出同一指令。实时与预测两条整日轨迹的指令差还混有灯热和反馈状态变化，不能直接量化预测独立节电。

六份原始回放位于 `evidence/joint-replays/`。各自哈希、分项适配哈希和网页载荷哈希见 [`data/joint-evidence-manifest.json`](../data/joint-evidence-manifest.json)；四区空间载荷哈希见 [`data/joint-space-evidence-manifest.json`](../data/joint-space-evidence-manifest.json)。复现入口使用当前仓库文件，不依赖原工作区的 `outputs` 目录或任何绝对路径。项目的开源底座许可及改造说明见 [`LICENSE`](../LICENSE) 和 [`NOTICE.md`](../NOTICE.md)。

首页的[预测贡献展示载荷](../data/joint-forecast-contribution-data.js)另从下述固定照明消融JSON提取六组名义电量、动作次数和温度可比状态。运行 `node scripts/build-forecast-contribution.cjs` 默认只读比对已保存载荷与消融文件，不重跑回放或写文件；`tests/joint-evidence-website.test.cjs` 还检查六组映射及网站引用。该展示载荷不是新的现场验证。

## 固定照明下的预测空调消融（本地证据；首页展示摘要）

运行 `node scripts/forecast-fixed-light-ablation.cjs` 会重算并逐字核对 [`forecast-fixed-light-ablation.json`](forecast-fixed-light-ablation.json)；脚本使用内置模块，不安装依赖，也不修改六份原始回放。每个日期与混合系数各运行日常基准、实时感知、预测协同三种空调策略。三者的42根18 W灯在06:30—22:30全部开启，灯位热量、人数代理、天气、建筑热模型和初始条件一致。基准空调用电及终态温度还必须与对应冻结原始回放一致。这样隔离的是**固定照明情景下，实时保持当前人数与调用冻结人数预测的空调策略差异**；闭环反馈导致随后室温和指令轨迹不同，是策略作用的一部分。

| 日期 | 混合假设 W/K | 实时空调 kWh | 预测空调 kWh | 预测－实时 kWh | 两者温度约束达标 | 终态最大温差 ℃ |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| 6/29 | 300 | 168.606 | 165.240 | −3.366 | 否 | 2.700 |
| 6/29 | 1000 | 172.163 | 169.754 | −2.410 | 是 | 2.203 |
| 6/29 | 5000 | 172.469 | 170.748 | −1.721 | 是 | 1.034 |
| 6/30 | 300 | 153.115 | 153.230 | +0.115 | 否 | 0.099 |
| 6/30 | 1000 | 157.055 | 157.437 | +0.383 | 是 | 0.204 |
| 6/30 | 5000 | 157.475 | 157.475 | 0.000 | 是 | 0.000 |

“达标”只指模型中的有人区22.2—26.8℃、空区20—28℃边界；它不代表现场舒适度验证。现行可比性门槛还要求两种策略都达标且四区终态温差不超过0.05℃。按这个门槛，只有6/30、5000 W/K一组可比，但预测与实时指令完全相同、空调用电也相同。其余组即使预测数值较低，也不能报告为合格节电。5000 W/K强混合没有现场校准，不能据此断言真实建筑中没有预测价值。固定全开照明情景下的桌面300 lx模型筛查也未对所有代理占用者达标；这些结果仅用于识别预测动作和能源差的来源，不是完整服务条件下的节电效果。

## 日终显热状态核算（不折算为电量）

运行 `node scripts/forecast-terminal-state-ledger.cjs` 会核对 [`forecast-terminal-state-ledger.json`](forecast-terminal-state-ledger.json)。它读取上面的固定照明消融终温和同一四区热容参数，逐区计算 `C区 × (预测终温 − 实时终温) / 3600000`，单位为kWh显热；同时用六份冻结原始回放中的基准储热量交叉核对热容计算。正值表示预测轨迹在22:30结束时较热。

| 日期 | 混合假设 W/K | 预测比实时多储存显热，默认10倍热容 kWh热 | 固定终温下5—20倍热容核算范围 kWh热 |
| --- | ---: | ---: | ---: |
| 6/29 | 300 | +7.190 | +3.595 至 +14.379 |
| 6/29 | 1000 | +5.108 | +2.554 至 +10.217 |
| 6/29 | 5000 | +3.716 | +1.858 至 +7.432 |
| 6/30 | 300 | −0.240 | −0.479 至 −0.120 |
| 6/30 | 1000 | −0.531 | −1.063 至 −0.266 |
| 6/30 | 5000 | 0.000 | 0.000 |

5倍和20倍两列**只改变储热核算系数**，保持默认10倍模型产生的终温不变；它们不是重新运行控制器后的结果。等效热容本身未经校准，显热差也不等于以后必须补充的制冷量：夜间室外交换、下一日天气、开机状态和人员到达会影响后续需求。因此不使用理论COP把这张表折算成“恢复电量”，也不从当日名义电量差扣出新的节电百分比。若要比较同等终态条件，须先约定共同恢复的时段与条件并真实回放，或修改控制目标使两条轨迹自然达到相同终态。

## 日终状态收敛候选（探索性；首页仅提示稳健性结论）

运行 `node scripts/forecast-terminal-guard-candidate.cjs` 重算并核对 [`forecast-terminal-guard-candidate.json`](forecast-terminal-guard-candidate.json)。候选在每个5分钟决策点维护一条使用当前人数保持策略的模型“影子轨迹”，用当前已知的预约代理和天气向前模拟5分钟。预测指令若使四区中任一区与影子轨迹的温差超过从约1.5℃逐步收紧至日终0.05℃的启发式边界，就在满足设备保持时间的指令中，先按单时段模型温度边界、再按偏离量与名义电量择优。影子轨迹的能耗、指令哈希和四区终温必须复现固定照明消融中的实时模式；没有向控制器泄漏下一时段实际人数或未来实际天气。该边界是在检查过6月29—30日结果后提出的探索性规则，不能把同两天再次运行称为独立验证。

| 日期 | 混合 W/K | 候选－实时名义空调 kWh | 终态最大温差 ℃ | 双方温度边界及终态均达标 | 改选指令次数 |
| --- | ---: | ---: | ---: | --- | ---: |
| 6/29 | 300 | 0.000 | 0.000 | 否，双方温度越界 | 4 |
| 6/29 | 1000 | −0.0765 | 0.042 | 是，仅当前15秒步长 | 9 |
| 6/29 | 5000 | −0.4973 | 0.438 | 否，终态未收敛 | 3 |
| 6/30 | 300 | −0.6120 | 0.393 | 否，温度越界且终态未收敛 | 6 |
| 6/30 | 1000 | −0.3060 | 0.231 | 否，终态未收敛 | 16 |
| 6/30 | 5000 | 0.000 | 0.000 | 是，但策略相同 | 0 |

唯一出现非零且终态达标的6/29、1000 W/K结果只有0.0765 kWh名义差。运行 `node scripts/forecast-terminal-guard-candidate.cjs --sensitivity` 核对 [`forecast-terminal-guard-step-sensitivity.json`](forecast-terminal-guard-step-sensitivity.json)：同一情景在5秒步长下差额为−1.275 kWh、终温差1.046℃，不达标；15秒时为−0.0765 kWh、0.042℃；60秒时指令与能耗完全相同。故这一微小差异**不具有步长稳健性**，不能作为预测节电的路演数字。影子室温是未经现场校准的模型值，不是传感器读数；全开灯的300 lx模型筛查也未对所有代理占用者通过。候选只说明一种可计算的闭环约束及其失败边界，尚不能替换现有网站策略或宣称现场节电。
